Abstract

Using large language models (LLMs) to turn a natural-language requirement for a multi-agent system into controllers that remain correct under shared-resource contention presents a key challenge: LLMs can readily decompose tasks but provide no correctness guarantees, whereas reactive synthesis is correct by construction but requires hand-written specifications. We introduce a neuro-symbolic framework in which LLMs translate and decompose the NL requirements into per-agent Assume‑Guarantee (A/G) contracts and a pipeline of certificate-ladder checks (specification grounding, compositional decomposition with mechanical contract completion, GR(1) synthesis with strategy validation, and runtime conformance) — a decomposition has no unique ground truth. Each failed check returns a witness traceable to one contract, driving targeted LLM repair. Certified controller strategies execute on a simulated control-barrier-function layer and hold mutual exclusion and freedom from starvation against every environment interleaving. If execution fails, runtime conformance feeds the detected violations back into the LLM repair process.

Shared Charging Station

Resource: charging station · capacity 1

N robots keep working until their battery runs low. During every low-battery episode a robot requests the shared charger, drives to it, and charges once it holds exclusive access — the arbiter guarantees fair, mutually-exclusive service so no robot is ever left waiting forever.

Full requirement spec (charger.yaml)
  • Each robot works. During every low-battery episode it requests the shared charger, drives to it, and charges once access and the charger location are available.
  • A robot must hold the charging station's exclusive access before it starts charging.
  • At most one robot may charge at the station at a time.
  • A robot can charge only while it is at the charging station.
  • A robot drives to the charger only while it is requesting and its battery remains low.
  • If a robot remains low-battery, is still requesting, and is not at the charger, it keeps driving back until it arrives; once arrived while still requesting, it is not displaced before grant.
  • The arbiter provides fair exclusive access: every request that remains asserted is eventually granted, and a grant persists only while the matching request persists.
  • Robot count N is varied across 3, 5 and 7 to test how the certificate ladder and synthesis scale with team size.

Corridor Contention

Resource: single-lane corridor · passage-type lock

Robots cross a single-lane corridor from side A to side B whenever the world demands a crossing. Only one robot may be inside at a time, and once the arbiter grants access it holds that grant for the whole crossing — never revoking it mid-passage — while still guaranteeing every standing demand is eventually served.

Full requirement spec (corridor.yaml)
  • Each robot crosses from side A through the corridor to side B when the world demands a crossing.
  • A robot must hold the corridor's exclusive access before it enters and starts crossing.
  • At most one robot may be inside the corridor at a time.
  • A robot is inside the corridor (crossing) only while it holds the corridor access.
  • Once granted, the arbiter keeps that grant for as long as the demand stands — no revoking a standing access mid-crossing (hold until release).
  • Every standing access demand is eventually granted; no robot's demand starves.
  • The crossing demand is raised and withdrawn by the world, not chosen by the robots, and keeps recurring.
N = 3

Shared Shelf & Dock

Resources: shelf & dock · independent arbiters

N robots continuously fetch items from a shared shelf and deliver them to a shared dock. Two independent arbiters — one per resource — grant exclusive access, since holding the shelf and holding the dock are never mutually exclusive with each other. A robot may travel and wait freely; only the final pickup or drop-off step requires the matching grant, and every request is eventually served.

Full requirement spec (multi_robot.yaml)
  • Each robot repeatedly fetches an item from the shelf and delivers it to the dock.
  • A robot must hold the shelf's exclusive access before picking up; it may navigate toward the dock as soon as it is carrying an item without needing the dock's grant just to travel there or wait nearby — only entering/occupying the dock to drop off requires the grant.
  • A shelf arbiter and a separate dock arbiter each grant at most one robot at a time on their own resource; the two arbiters do not constrain each other, and a robot may hold both grants at once.
  • Each arbiter provides fair access: every standing request is eventually granted, and a grant persists while the request persists (no one-step pulses).
  • After completing pickup or dropoff, a robot releases its resource request and lease immediately, so the arbiter can serve the next waiting robot without delay.
  • A robot can pick up only while at the shelf, and drop off only while at the dock carrying an item.
  • Each robot should keep completing deliveries indefinitely.
  • Robot count N is varied across 3, 4 and 5 to stress-test the two-arbiter decomposition.

Two-Layer Dock

Resource: shared dock · independent pickup points

Each robot fetches items from its own, unshared pickup location but must deliver to one shared dock. A single arbiter grants exclusive dock access so only one robot occupies it at a time, fairly serving every standing request so deliveries keep completing indefinitely.

Full requirement spec (two_layer_dock.yaml)
  • Each robot repeatedly fetches an item from its pickup location and delivers it to the shared dock.
  • A robot must hold the dock's exclusive access before using the dock.
  • At most one robot may hold the dock at a time.
  • A robot can pick up only while at its pickup location, and drop off only while at the dock carrying an item.
  • Each robot does one thing at a time and should keep completing deliveries indefinitely.
  • World behaviour: when a robot heads somewhere it eventually arrives; a standing request for dock access is eventually granted; new tasks keep arriving over time.
N = 4
